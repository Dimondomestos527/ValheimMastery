# Engine Implementation Reference

Curated 2026-10-04 for Mastery 1.4.123 / installed Valheim 1.0.16. Applied guidance; not authority for current gameplay implementation. Consult only relevant topics. Resolve conflicts using [REFERENCE_INDEX](REFERENCE_INDEX.md).

## Local anchors before external advice

Read-only inspection of both installed native `assembly_valheim` variants found Version initialization 1.0.16, network version 40, and selected native lifecycle/ownership/player-save/inventory/teleport entry points. Both native SoftReference assemblies expose LoadAsync, IsLoaded and Release. This establishes signatures/version, not correctness of their use.

Existing runtime logs record Unity **6000.0.75f1**, BepInEx **5.4.23.5** and Harmony **2.9.0**. This project targets **netstandard2.1**; compile packages BepInEx.Core 5.4.21 / HarmonyX 2.10.2 are distinct from loaded runtime versions. Unity links below deliberately use **6000.0**, the matching documentation family, not a claim that every current manual sentence was tested on patch .75. Inspect native assemblies for API availability or patch-specific differences.

Current reuse points: MasteryPlugin initialization/ticks; NativeSoftVisualAssets held references and scene release; VfxPool baseline restoration/leases; PerkAudioService; shared material ownership in PhaseAVfx; event/hit context and transient state. Their canonical boundaries are in [SHARED_SYSTEMS](../architecture/SHARED_SYSTEMS.md). Never replace these foundations merely to copy an external example.

## Lifecycle and object composition

The DO/AVOID columns are Mastery engineering recommendations, not claims that every existing consumer already follows them.

| Topic | WHY IT MATTERS TO MASTERY | DO | AVOID | WHEN TO CONSULT THE ORIGINAL DOCUMENTATION |
|---|---|---|---|---|
| GameObject/Component/MonoBehaviour lifecycle | Plugin startup, spawned effects and scene objects have different readiness. | Initialize owned state in Awake; prepare each reuse separately; pair enabled subscriptions with cleanup. | Assuming Start repeats on pool checkout or that Awake means player/network/assets are ready. | New components or pooled activation: [U01](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.Awake.html) ([OnEnable](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.OnEnable.html), [Start](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.Start.html)). |
| Execution order and hazards | Scene singleton and input/physics/animation state can be unavailable or from another phase. | Inspect the native caller; explicitly check readiness; choose the relevant callback. | Ordering unrelated objects' Awake by luck; global script-order changes to repair one perk. | Cross-component dependencies or frame-sensitive hooks: [U02](https://docs.unity3d.com/6000.0/Documentation/Manual/execution-order.html) and [U01](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.Awake.html). |
| Prefab/runtime instantiation | A native donor can include damage, networking, AI or self-destruction. Active clones may run Awake/OnEnable during Instantiate. | Inspect components and native lifecycle first; build a safe cosmetic template through existing sanitation before activation. | Instantiate an active attack prefab and hope later component removal prevents side effects; globally deactivate/mutate the donor. | Selecting a donor or changing activation order: [U03](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Object.Instantiate.html) plus actual donor inspection. |
| Transforms/local versus world space | Weapon/target attachment, zones and portal movement can shift or scale cues incorrectly. | State the coordinate space; set parent/position/rotation deliberately; recheck after teleport/reparent. | Mixing world offsets with local coordinates; assuming parent scale is harmless. | Following effects, offsets, nonuniform scale or SetParent behavior: [U04](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Transform.SetParent.html). |
| ParticleSystem | A moving aura and stationary impact require different particle behavior. | Choose simulation space; reset changed modules and emitted state; bound rate/lifetime. | Assuming parenting also changes existing world-space particles; leaking old particles into a pooled cue. | Particle follow, scale or reuse changes: [U05](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/ParticleSystem.MainModule-simulationSpace.html) and the specific module API. |
| Trails, line renderers and lights | Composed native cues can leave teleport streaks or excessive brightness. | Clear trails on reuse/teleport; choose line space; bound light range, intensity and concurrency. | Stale trail points, global line coordinates on a local attachment, unrestricted lights. | Changing trail reset/line coordinates/light settings: [U06](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TrailRenderer.Clear.html) ([LineRenderer](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/LineRenderer-useWorldSpace.html), [Light](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Light.html)). |
| Materials/renderers and instance safety | A shared donor material change can alter vanilla and other players' effects. | Prefer instance property overrides where suitable; otherwise track/dispose owned material copies through current services. | Editing shared donor materials; reading renderer.material repeatedly without accounting for instantiation; destroying borrowed resources. | Tint/shader/material ownership work: [U07](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Renderer-material.html) plus current owned-material implementation. |
| AudioSource and spatial sound | Owner confirmation and world impacts need different audiences and repeat rules. | Reuse PerkAudioService/native clip settings; specify 2D/3D mix, rolloff, volume, repeat limits and stop behavior. | Treating spatial sound as networking; playing twice through local and remote paths; instantiating an attack donor for its sound. | Spatial mix or native-source tuning: [U08](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/AudioSource-spatialBlend.html) and the relevant AudioSource property API. |

## Lifetime, loading and performance

| Topic | WHY IT MATTERS TO MASTERY | DO | AVOID | WHEN TO CONSULT THE ORIGINAL DOCUMENTATION |
|---|---|---|---|---|
| Object pooling | Frequent procs can repeatedly create/destroy expensive hierarchies. | Reuse VfxPool; reset transforms, particles, audio, materials and timers; cap retained/active objects. | Pooling without a full reset; double returns; replacing the pool merely because Unity has a generic example. | Extending lease/release behavior: [U09](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Pool.ObjectPool_1.html). Its generic pool is not thread-safe; inspect actual Mastery limits. |
| Allocation/GC | Hit/proc/frame paths multiply small allocations across actors. | Measure frequency/allocation; cache scene-scoped lookups and reuse bounded buffers. | Per-proc world scans, LINQ/closure/string churn; blanket GC disable or forced collections as a mod-level cure. | Allocation regression: [U10](https://docs.unity3d.com/6000.0/Documentation/Manual/performance-optimizing-code-managed-memory.html); follow its relevant memory subtopic and verify measured gains. |
| Cleanup/lifetime | Pool return, scene unload and shutdown are different endpoints. | Make explicit release idempotent; invalidate scene caches; cancel stale callbacks; destroy only owned objects. | Delayed Destroy on an object that may be returned/released then reused; treating OnDestroy as a durable-save or crash-recovery guarantee. | Destruction timing/callback coverage: [U11](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Object.Destroy.html) ([OnDestroy](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.OnDestroy.html)). |
| Headless dedicated server | Gameplay must work without rendering/audio readiness. | Inspect actual Valheim batch/server paths; keep authoritative state independent of VFX/SFX; guard client-only operations. | Inferring a visible cue from a headless test; assuming the installed server used every Unity Dedicated Server build optimization. | Client/server divergence: [U12](https://docs.unity3d.com/6000.0/Documentation/Manual/dedicated-server-optimizations.html) plus installed native evidence. |
| Async resource loading | Native assets can be indexed yet pending; a caller/scene can disappear before completion. | Reuse native SoftReference wrappers; distinguish absent/pending/loaded; retain/release references; bound retry and reject stale work. | Synchronous bundle waits, tight polling, treating pending as permanently absent, new per-perk loaders. | New loading path: native SoftReference assembly + NativeSoftVisualAssets first; [U13](https://docs.unity3d.com/6000.0/Documentation/Manual/async-await-support.html) for general async semantics, not a substitute Addressables contract. |
| Unity main-thread assumptions | Background continuation can touch destroyed Unity objects or unsafe APIs. | Treat Unity object access as main-thread work unless explicitly documented otherwise; verify callback context and lifetime. | Task.Run around GameObject/inventory mutation; .Wait/.Result in the frame loop; guessing that async means background-safe. | Adding tasks/continuations: [U13 continuation](https://docs.unity3d.com/6000.0/Documentation/Manual/async-awaitable-continuations.html). New Awaitable examples require installed-API review. |
| C# hot-path performance | Combat and service ticks need predictable cost under multiplayer load. | Measure before/after; use appropriate collections and avoid repeated reflection; review value-copy costs. | Changing everything to structs, unsafe code or new framework APIs without evidence; sacrificing transaction correctness for speculative speed. | A measured hot path: [C01](https://learn.microsoft.com/en-us/dotnet/csharp/advanced-topics/performance/) plus Unity memory guidance. Modern .NET examples need Mono/netstandard2.1 compatibility checks. |
| Event/state/component design | Perks share hit context, authority and lifecycle; duplicate publishers can double rewards. | Reuse existing payloads/services where semantics fit; unsubscribe scene-bound consumers; explicitly choose transient/player/world state. | Assuming every declared event publishes everywhere; storing durable cargo/Favor only in a component or weak table; creating a competing event bus. | Subscription/lifetime change: [C02](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/events/how-to-subscribe-to-and-unsubscribe-from-events) and current publisher/subscriber/source trace. |

| Plugin lifecycle | MasteryPlugin wires config, assets, Harmony and service ticks. | Extend existing ordered initialization/shutdown; scope ownership and cleanup explicitly. | Independent per-perk plugins/patch registration or assuming Awake has a loaded world. | Initialization/teardown edits: [B01](https://docs.bepinex.dev/articles/dev_guide/plugin_tutorial/2_plugin_start.html) and MasteryPlugin. ## Harmony selection and compatibility

| Topic | WHY IT MATTERS TO MASTERY | DO | AVOID | WHEN TO CONSULT THE ORIGINAL DOCUMENTATION |
|---|---|---|---|---|
| Prefix | Eligibility, arguments or pre-action context must sometimes be inspected before vanilla. | Use for necessary preconditions/context; skip original only when full replacement is intentional and reviewed. | Broad return-false overrides for small side effects; forgetting other side-effecting prefixes can be skipped. | Argument/result/skip work: [H01](https://harmony.pardeike.net/v2/articles/patching-prefix.html). |
| Postfix | Many bonuses can follow native execution without replacing its whole behavior. | Prefer after-result integration where suitable; verify the action actually succeeded before granting rewards. | Assuming a postfix proves the original ran or succeeded; relying on it for exception-path cleanup. | After-action/result changes: [H01 Postfix](https://harmony.pardeike.net/v2/articles/patching-postfix.html). |
| Transpiler | Some precise interior changes cannot be expressed at entry/exit. | Inspect current native IL in both variants; use meaningful anchors, preserve labels/exception blocks, validate matches and coexistence. | Fixed instruction offsets/counts; copying historical IL; silent partial edits on mismatch. | Only when simpler hooks cannot express the change: [H02](https://harmony.pardeike.net/v2/articles/patching-transpiler.html). |
| Finalizer | Shared hit/context/transaction guards may require cleanup even when patched code throws. | Restore owned context/guards idempotently; preserve/report exceptions unless suppression is explicitly justified. | Treating postfix as finally; blanket exception swallowing that hides state corruption. | Failure-path cleanup: [H03](https://harmony.pardeike.net/v2/articles/patching-finalizer.html). |
| Patch compatibility / minimal patches | Other mods and native version changes can alter order and execution. | Target the narrowest sufficient hook; inspect existing patches and compile gates; document necessary ordering; unpatch only Mastery's own ID. | Assuming load order equals execution order; global unpatching; maximum-priority patches by habit; claiming registration proves gameplay. | Conflicts, generics/inlining, startup or missing calls: [H04](https://harmony.pardeike.net/v2/articles/priorities.html) ([edge cases](https://harmony.pardeike.net/v2/articles/patching-edgecases.html)). |

Stable Harmony documentation explains general 2.x behavior. Mastery's compile HarmonyX package and loaded Harmony assembly must still be inspected for differences; the documentation does not authorize replacement or upgrade. “Minimal patch” means the smallest sufficient intervention, not an absolute ban on prefixes or transpilers.

## Applied review questions

Check the affected native hook and compile gate; who owns/validates state; readiness before mutation; generated-hit recursion; acquired resources and every exit path; scene/owner/reconnect behavior; cold-load presentation; and frequency/concurrency cost. Choose only dimensions relevant to the task. Static/source checks, runtime resolution and manual player acceptance remain separate evidence classes.

All presentation remains subject to the [vanilla-only asset workflow](../architecture/VANILLA_ASSET_WORKFLOW.md). Unity tutorials allowing imported art do not override that policy. This file neither approves new gameplay nor closes the migration regression baseline.
