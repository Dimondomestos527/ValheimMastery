## Approved boundary

For authenticated current-world kind2 reply matching current player's exact receipt token, already durable phase3 Applied or phase4 Cancelled can transition to phase5 Settled in m_customData without immediate full character save. Keep all original phase1 Requested, phase2 Uncertain BEFORE native effect/payment, phase3 Applied AFTER native payment and phase4 cancellation persistence boundaries. The successful path reduces four full profile saves to three. Phase5 is local cleanup/permission to begin another operation, not proof of payment.

Reason: phase3 Tick sends kind3 with the SAME token/output. Server ACKs only matching durable Applied entry (player/type/output) or Confirm whose Store.Apply durable write succeeded. Phase4 Tick sends kind4, which ACKs only matching durable Closed entry/player; loaded cancellation cannot recreate revocation. Store.Ready required; write failure marks unavailable. AdmissionStore retains all token tombstones, refuses capacity4096 instead of evicting them. Terminal queries do not instantiate, debit, refund or grant a new execution nonce; they precede fresh enable/unlock admission gates.

Crash after in-memory Settled but before next profile save leaves durable phase3/4, so repeat terminal query and settle again. After new intent starts, mandatory phase1 full save must succeed BEFORE sending its request: durable new token replaces old receipt only after old server terminal is already durable. A failed phase1 save cannot issue a request. Existing save-failure semantics remain unknown/fail-closed; never infer disk unchanged from false.

Requirements: keep token/player/world/output exact; permit this memory-only operation solely from the checked phase3/4 kind2 terminal ACK branch; don't expose a generic arbitrary phase5 setter as payment authority. Validate original phase/output before mutation and preserve receipt/key if serialization fails. Local Current may clear only when matching token; late prior ACK must never clear a newer intent. Duplicate ACK with phase5 is harmless. World/session/character checks stay mandatory. Natural later profile saves may persist phase5; it needs no rollback of inventory or world state.

**Do not globally remove full saves from all Save(...,5,...) calls.** Placement.Reply also uses phase5 on kind-1 rejection while the receipt may still be Requested. That reply is not necessarily backed by a durable terminal tombstone: e.g. failed reserve/save can return rejection. This separate boundary is not approved by the successful Applied/Closed argument. Keep its original persistence and treatment until separately reviewed. No timeout/missing object/config change may manufacture Settled.

## Compact Requested journal

NOT APPROVED as a simple independent-file substitution. A sidecar introduces a second durable character identity/intent store plus profile/inventory save ordering. If request/admission exists but profile lacks the token, reconnect can lose pending ownership and strand a server hold; if sidecar survives a profile rollback or comes from another world/character/save lineage, treating it as Applied or reusable permission can duplicate/reconstruct payment incorrectly. Requested does not prove debit. Server absence or missing world object cannot revoke an issued unknown operation.

An independent WAL could be designed, but requires explicit token/world/character/profile-lineage binding, durable monotonic stages, discovery and reconciliation before any new action, phase2+inventory boundary, phase3+postpayment inventory durability, terminal tombstone retention, save failure/cloud writer behavior, sidecar/profile rollback and migration protocol. An atomic file write alone does not provide atomic profile/inventory consistency. Current proposal does not provide that protocol; keep phase1 full save.
